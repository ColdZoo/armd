## 1. 概要

2026-11-22 23:0x，遥操作（teleop）把 Koch v1.1 从臂（follower，`/dev/cu.usbmodem5A7C1190831`）
的**肘部关节（motor 3）**顶到机械限位并持续输出力矩，舵机触发并**锁存 `hardware error 0x80`**。
armd v0.1.0 的 follower worker 从此进入「读失败 → 掉线 → 重连」循环，且**永远无法恢复**：

- `sync_read` 只要收到任一电机的状态包 error 位非 0 就整次失败 → 连续 3 次 → `connected=false`（~50ms 内）；
- 自动重连的 `open_io()` 在**打开成功后才覆盖** `self.io`，失败路径保留旧串口 handle；
  而串口被 `serialport` 以 `TIOCEXCL` 独占 → **自己持有的旧 fd 让后续 open 永远 `Device or resource busy`**；
- 断线后 `run()` 循环 `next_poll` 停在过去、`poll()` 被跳过 → `wait=0` → `spin_loop()` **100% CPU 空转**；
- worker 线程并未退出，但该臂不再轮询、状态帧停发，客户端在处置期重启风暴中被断开（`BrokenPipe`）；
- 唯一恢复手段是 `launchctl bootout` + `bootstrap` **完整重启**（释放 fd）**加物理断电**（清 0x80）。

现场过程：23:23 启动的进程 `77101` 以 **100.1–100.6% CPU** 空转近 30 分钟，follower 一直
`connected=false, error="Device or resource busy"`；期间设备节点消失又重枚举，旧/新 fd 均被保留。
**23:52:56 完整重启后**（新进程 `84036`，仍是 v0.1.0 二进制）两臂恢复 **60.5Hz**、每个串口设备恰好
1 个 fd、CPU 降到 4.2% —— 这反证 v0.1.0 只能靠重启恢复，根因未除。

## 2. 现象与影响链

### 2.1 触发：遥操作把肘部顶到机械限位

- teleop 以 60Hz 对从臂 `Goal_Position(116)` 做 `sync_write`；上层虽按 EEPROM 限位做了 clamp，但
  **EEPROM 限位 ≠ 机械行程**（已知坑 1：肘部 EEPROM `Max_Position_Limit=3309`，机械可动范围更短），
  因此目标仍在可行范围但机械已顶死 → 电机持续输出力矩。
- 时间足够长后舵机自行保护，状态包 error 字节置位 `0x80`（X 系列 `hardware_alert`；项目位定义见
  `docs/SAFETY-DESIGN.md` §3.3），且该位**锁存**：限位解除、温度回落都不会自动清，直到 Reboot 或断电。

### 2.2 固件层：0x80 锁存但仍能回包

- 锁存后舵机**并没有从总线上消失**：它继续回应 `SYNC_READ` / `PING`，只是状态包的 Error 字节为 `0x80`。
  这一点决定了后续故障形态（不是"设备离线"，而是"读请求本身变成错误"），也说明 **Reboot 指令大概率仍可达**
  （`⏳ 待真机复现验证`）。
- 现场观察：只有物理断电后 0x80 才消失（zeropose「事故记录」）。这与 X 系列 hardware error 的锁存语义一致。

### 2.3 armd worker 层：一个电机的 error 位 = 整条总线读失败

v0.1.0 的链路（代码见 §3.2）：

```
sync_read(132,4,ids=1..6)          # 每帧一次，60Hz
  └─ read_status(None) 收到任一状态包 -> st.error != 0 -> Err(IoError::Device)
       └─ sync_read 把 Device 当整次读失败返回 Err
            └─ poll(): errors_in_row += 1
                 └─ 连续 3 次 -> connected=false, 发布 event:"arm" connected:false
                      └─ state 不再更新：joints/seq/hz/read_us 冻结，state 帧停发
```

- 60Hz 下一帧 ~16.7ms，**3 帧约 50ms** 就判定整臂掉线，而不是"motor 3 有问题"。
- 掉线后自动重连的**握手要求全部 6 个电机 `ping` 成功**（`ok == motors.len()`）；motor 3 的 0x80 未清，
  握手永远失败 → `connected` 永远 false。**即使另外 5 个电机完全正常，整条从臂也不可用。**

### 2.4 fd 层：旧 handle 不释放 → 独占串口永久 EBUSY

- 重连路径 `ensure_connected()` 直接调用 `open_io()`；`open_io()` 是 `let p = DxlPort::open(...)?;
  self.io = Some(...)` —— **open 失败时 `?` 提前返回，旧 `self.io` 原封不动**。
- 而旧 `self.io` 持有的 fd 是以 **`TIOCEXCL` 独占**方式打开的（serialport 4.10.1 默认 `exclusive = true`），
  于是下一次 open 必然 `Device or resource busy`（**同进程打开也不行**，本机 23:24–23:52 实证）。
- 死锁：**自己占着 fd → 永远 open 不了 → 永远不释放 fd**。旧 fd 不会超时、不会被 GC，只能由进程退出释放。
- 手动 RPC `arm.reconnect` 是 v0.1.0 唯一会先 `self.io = None`（释放）的路径，但自动重连**永远不经过它**；
  且 RPC 的 `Cmd::Reconnect` 在 `dispatch` 里还会先因 `io.is_none()` 分支尝试一次 open（见 §3.3）。

### 2.5 客户端层：状态流停更 + BrokenPipe

- 从臂 `connected=false` 后**状态帧停发**（`publish_state` 只在 poll 成功时调用），HUD/teleop/armstrike
  bridge 侧该臂数据冻结、`hz=0`、`seq` 不再增长。
- 处置期 armd 被反复重启（18 次启动序列）：每次进程退出，内核关闭其全部客户端连接；Unix socket 文件被删/重建
  （`server.rs:114-131`）。v0.1.0 的 Python 客户端**没有自动重连**（`clients/python/armd_client.py`：
  `_send` 直接 `sock.sendall`，`request` 无重试；仅有一个 `arm.reconnect` RPC 包装方法），
  因此客户端在下一次写请求时直接收到 `BrokenPipeError`；留在旧进程上的订阅也随进程消失（`🟡 高置信推断`：
  机制由代码确定，但当时各客户端的具体异常栈未逐一留存）。
- 因为「RPC 服务还在、只是某条臂坏」，故障表现为**静默的臂离线**（页面/脚本卡住）而不是服务崩溃，容易被误判。

### 2.6 恢复层：为什么必须"完整重启 + 物理断电"

| 处置 | 效果 | 原因 |
|---|---|---|
| `launchctl kickstart`（重启进程） | v0.1.0 下**不够**（现场记录：普通 kickstart 不行） | 若进程未被真正替换（KeepAlive 认为仍在跑），旧 fd 仍在；仅信号无法让 worker 释放 handle（无 stop 时 drop 逻辑） |
| `launchctl bootout` + `bootstrap`（完整重启） | 释放 fd，open 恢复 | 进程退出 → 全部 fd 关闭 → `TIOCEXCL`/flock 释放；**23:52:56 实测：重启后两臂 60.5Hz、每设备 1 fd** |
| 物理断电（断从臂 12V） | 清 0x80 | hardware error 位锁存，软件侧无 Reboot/清错通道（根因 D） |
| 只修 0x80、不重启 | 无效 | 旧 fd 仍自锁串口，重连永远 EBUSY（根因 C） |

### 2.7 影响链总图

```
teleop 60Hz 写 Goal_Position(116)
  └─> 从臂肘部 motor 3 顶机械限位（EEPROM 限位 ≠ 机械行程）· 持续力矩
       └─> 舵机 latch Hardware Error 0x80（仍能回包，状态包 error=0x80）
            └─> [B] read_status() Err(Device) → sync_read 整次 Err → poll 连续 3 次 → connected=false
                 ├─> 状态帧停发（joints/seq/hz 冻结）→ HUD/teleop 失去从臂
                 └─> [C] 自动重连 open_io() 失败仍保留旧 handle
                      ├─ 旧 fd 持 TIOCEXCL → 后续 open 永远 EBUSY（自己锁死自己）
                      └─> [E] 断线循环 next_poll 过期 + poll 跳过 → wait=0 → spin_loop → 100% CPU
                           └─> 处置期反复重启 → 客户端旧连接 BrokenPipe
                                └─> 唯一恢复：bootout+bootstrap（释放 fd）+ 物理断电（清 0x80）
                                     └─> v0.1.0 根因未除，下一次 stall 会再次复发
```

影响面：`koch_v1_1:follower` 整臂（6 个电机）读/写全部不可用；`koch_v1_1:leader` 不受影响
（23:26 证据：leader `connected=true, hz=60.4, seq=8073`）。依赖从臂的功能（遥操作跟随、零位标定、
Web 控制台、游戏手柄 bridge）全部中断；armd 进程本身仍存活、RPC 仍可响应（只是从臂报错）。

### 3.2 根因 B：单个电机硬件错误拖垮整臂 worker —— `✅ 已证实`

**证据 1**：`read_status` 只要解出状态包且 `error != 0` 就立刻返回 `Err(Device)`——
**先判 error，后判目标 id**，所以连"顺手收到的其它电机错误包"也会炸掉本次读。
`src/port.rs:86-98`：

```rust

    loop {
        if !self.buf.is_empty() {
            match dxl::decode(&self.buf) {
                Ok((st, used)) => {
                    self.buf.drain(..used);
                    if st.error != 0 {
                        return Err(IoError::Device { id: st.id, error: st.error });
                    }
                    if want.is_none() || want == Some(st.id) {
                        return Ok(st);
                    }
                    continue;
                }
```

### 3.3 根因 C：reopen 失败路径不 drop 旧 handle → fd 泄漏 → 永久 EBUSY —— `✅ 已证实`

**证据 1（关键 3 行）**：`open_io` 先 open、成功后才覆盖 `self.io`；失败时 `?` 提前返回，旧 handle 原地保留。
`src/arm.rs:277-285`：

```rust

fn open_io(&mut self) -> Result<(), IoError> {
    if self.cfg.sim {
        self.io = Some(Box::new(SimPort::new(&self.cfg.motors)));
        return Ok(());
    }
    let p = DxlPort::open(&self.cfg.port, self.cfg.baud)?;   // ← 失败时旧 self.io 不会被替换/丢弃

}
```

**证据 2**：`ensure_connected` 每次重连直接 `open_io()`，失败路径只改 state/广播事件，**从不先把
`self.io` 置 None**（`src/arm.rs:287-329`，见 §3.2 证据 4 的同段代码）；open 成功但握手失败时
（`arm.rs:316-321`）也保留刚打开的 handle —— **两种失败都会把 fd 留下来**。

**证据 3**：串口是独占的。`serialport 4.10.1`（`Cargo.lock`）默认 `exclusive = true`：
`serialport-4.10.1/src/lib.rs:1057`（builder 默认 `exclusive: true`），
`src/posix/tty.rs:110-111`（"Ports are opened in exclusive mode by default"）、
`tty.rs:131-139`：

```rust
// serialport-4.10.1/src/posix/tty.rs (131-139)
// Set the requested access mode on the port. In exclusive mode use
// TIOCEXCL and an exclusive flock to prevent other openers. ...
if builder.exclusive {
    ioctl::tiocexcl(fd.0)?;
    flock::lock_exclusive(fd.0)?;
} else {
    flock::lock_shared(fd.0)?;
}
```

`armd` 自己的注释也承认这一点：`src/server.rs:625-626`——"串口独占（serialport 已设 TIOCEXCL）"。
macOS 上 `TIOCEXCL` 语义：设置后该 tty 的**任何后续 `open(2)` 都 EBUSY**，直到 `TIOCNXCL` 或
**该 tty 的所有 fd 关闭**；它并不豁免同一进程（本机实证：armd 自己被自己的 fd 挡住）。

**证据 4**：唯一的显式释放路径是手动 RPC。`src/arm.rs:534-539`：

```rust
// git show d085a63:src/arm.rs  (534-539)
Cmd::Reconnect => {
    self.connected = false;
    self.last_reconnect = Instant::now() - Duration::from_secs(3600);
    self.io = None;                       // ← 只有这里会 drop 旧 handle
    respond(Ok(json!({ "ok": true })));
}
```

对应 RPC `arm.reconnect` 在 `src/server.rs:525-528`。但自动重连 `ensure_connected()` **不经过** `Cmd::Reconnect`，
所以 v0.1.0 的自动重连永远不释放旧 fd。

**现场/复采印证（✅）**：

- 23:26 证据：`lsof` 显示 PID 77101 仍持有 `4u CHR ... /dev/cu.usbmodem5A7C1190831`，同一时刻
  `arm.list` follower `connected=false`（详见 §4）。viking 事故记录更早还观察到 fd 223。
- 23:26 之后设备节点以 `CHR 9,7` 重新出现（精确时刻未记录；devfs 的 mtime 不可靠），PID 77101 **成功 open 出新 fd 91u**（旧 tty 的 TIOCEXCL 不拦新 tty），
  但握手失败 → 新 handle 又被保留 → 再次 EBUSY（23:49/23:51 复采 `error="Device or resource busy"`）。
- **只有进程重启（23:52:56）才释放 fd**：新进程 84036 每设备 1 个 fd、两臂 60.5Hz。

**为什么 fd 永远 busy（一句话版）**：`open_io()` 把 `DxlPort::open` 放在赋值之前且用 `?` 提前返回 →
**失败不 close 旧 handle**；旧 handle 的 fd 带 `TIOCEXCL` → 下一次 open EBUSY；失败又不 close → 无限循环。
串口 fd 没有 GC/超时，只有 `drop`（=进程退出或 `self.io=None`）能释放。

### 3.4 根因 D：缺 Dynamixel Reboot(0x08) / clear error / torque_off —— `✅ 大体成立`（见 3.7 差异）

**证据 1**：指令集没有 Reboot。`src/dxl.rs:12-16`：

```rust
// git show d085a63:src/dxl.rs  (12-16)
pub const INST_PING: u8 = 0x01;
pub const INST_READ: u8 = 0x02;
pub const INST_WRITE: u8 = 0x03;
pub const INST_SYNC_READ: u8 = 0x82;
pub const INST_SYNC_WRITE: u8 = 0x83;
```

无 `INST_REBOOT = 0x08`、无 `reboot_packet()`；`src/dxl.rs:18-25` 也无 `Hardware_Error_Status(70)` /
`Min/Max Position Limit(48/50)` 地址常量 → 软件既不能清 latched error，也不能读错误状态。

**证据 2**：RPC 方法表（`src/server.rs:321-597`）无 `arm.reboot` / `arm.clear_error` / `arm.torque_off`；
最接近的是 `arm.torque`（`src/server.rs:507-519`）与 `arm.reconnect`（525-528）。

**证据 3（差异）**：`torque_off` **并非完全缺失**——`arm.torque` 的 `enable=false` 就是按电机写
`Torque_Enable(64)=0`（`server.rs:511-515`），可以手动实现 torque off。v0.1.0 真正缺的是：
(a) **自动** torque off（堵转/限位时主动卸力，属 A 的修复）；
(b) Reboot(0x08)；
(c) clear-error / 读 `Hardware_Error_Status`；
(d) 独立的 `arm.torque_off` 便捷方法（v0.2.0 §6 才新增）。

**结论**：D 成立（Reboot/清错通道确实没有，这是"断电复位"成为唯一清 0x80 手段的直接原因）；
但"缺 torque_off"应精确表述为"缺自动 torque off + 缺独立 RPC 便捷方法"，而非完全没有手动能力。

### 3.5 根因 E（额外发现）：断线后 worker 100% CPU 自旋 —— `✅ 已证实`

**证据 1**：轮询被 `connected` 门控，`next_poll` 的推进也在这扇门内；断线后 `next_poll` 永远停在过去。
`src/arm.rs:579-587`：

```rust
// git show d085a63:src/arm.rs  (579-587)
if self.connected && Instant::now() >= self.next_poll {
    self.poll();
    // 漂移无关的节拍：以上一次计划点为基准推进，避免睡眠误差累积
    let interval = self.cfg.poll_interval();
    self.next_poll += interval;
    if self.next_poll < Instant::now() {
        self.next_poll = Instant::now() + interval;
    }
}
```

**证据 2**：掉线路径不重置 `next_poll`（`arm.rs:466-472` 只清 `last_poll_at`），初始值也是
`Instant::now()`（`arm.rs:206`）。于是 `wait = next_poll.saturating_duration_since(now)` 恒为 0：

```rust
// git show d085a63:src/arm.rs  (588-596)
let wait = self.next_poll.saturating_duration_since(Instant::now());
let cap = Duration::from_millis(2);
let sleep_for = if wait > cap { cap } else { wait };
if sleep_for > Duration::from_micros(150) {
    std::thread::sleep(sleep_for);
} else {
    std::hint::spin_loop();
}
```

`wait=0` → `sleep_for=0` → 不 sleep，`spin_loop()` 空转。`ensure_connected` 的
`reconnect_sec`（默认 2s，`config.rs:17-19`）节流（`arm.rs:291-293`）只限制**真正 open** 的频率，
不限制空转；两次尝试之间的 ~2000 轮全部空转 → 单核 100%。

**证据 3（实测）**：`ps.txt`（23:26）`TIME=2:12.71 / ELAPSED=02:13 = 99.78%`，`%CPU=100.6`；
analyst 复采（23:51）`26:48.01 / 26:52 = 99.75%`，`%CPU=100.1`。且该自旋**不产生日志**（armd 只在启动写日志），
事故中很难从日志发现 CPU 异常。

### 3.7 与用户/现场记录表述的差异（需注意）

1. **D 的 `torque_off`**：v0.1.0 已有 `arm.torque`（`enable=false`，`src/server.rs:507-519`），可手动 torque off；
   缺的是「自动 torque off + 独立 `arm.torque_off` RPC + Reboot/清错」。验收/文档描述时应区分「能力」与「自动化」。
2. **"per-arm worker death"**：worker 线程**没有退出**，它仍存活、100% CPU 空转、仍消费 RPC 队列
   （对从臂的 `arm.read` 会走 stale io 返回错误/超时）；对外表现为该臂死亡。不要按"线程 panic/退出"去修。
3. **23:26 `arms.json` 的 error 是 `No such file or directory` 而不是 `Device or resource busy`**：
   因为采集时**设备节点已经消失**（USB 掉线/断电重枚举），worker 报的是最后一次 open 的 ENOENT。
   EBUSY 出现在「节点存在、旧 fd 仍持有」的时段（SAFETY-DESIGN §2 引用的 23:25 观测；analyst 23:49/23:51 复采）。
   引用证据时必须分两段，不能只贴 `arms.json` 一条就断言 EBUSY。
4. **fd 号不固定**：viking 记录 fd 223（更早的进程）、23:26 证据 fd 4u（PID 77101）、重枚举后 fd 91u
   （同一 PID 重新 open 成功）——都指向同一 bug，但**不能把某个 fd 号写死进断言**。
5. **viking「事故记录」的"已恢复"与现场不一致**：记录写于 ~23:10（称 bootout+bootstrap 后两臂恢复），
   但 23:23 启动的 PID 77101 在 23:25–23:52 一直故障；真实恢复点是 **23:52:56 的完整重启**（PID 84036）。
   中间是否又复发、断电发生在哪一刻，需 lead 核对操作时间线（`⏳`）。
6. **`frames_published` 会误导**：23:26 证据里 follower `polls=0` 但 `frames_published=1158`；复采时 29988。
   这些不是状态帧，而是"每次重连失败都向订阅者广播一条 event"的累计（失败次数 × 订阅者数）。
   监控应看 `polls/seq` 增量而不是 `frames_published`.

## 5. 复现与验收方法

### 5.1 无硬件层：sim 注入（v0.2.0）

v0.2.0 提供 `arm.sim.inject`（见 `docs/SAFETY-DESIGN.md` §3.2/§6），在 `--sim` 臂上可注入：
`stall`（位置冻结、velocity=0）、`hardware_error`（该电机状态包 error=0x80 且不返回 data）、
`no_response`（该电机不出现在回包）、`clear`（清除注入）。对应验收：

```bash
# 1) B/D：单电机硬件错误隔离 + reboot 清除
armd --sim --socket /tmp/armd-sim.sock &
#   arm.sim.inject kind=hardware_error motors=[3]  → arm.list: motor_errors["3"].code=128，
#      connected 仍 true，其他电机 joints 继续更新；arm.reboot motors=[3] → 清除、connected 不变
# 2) A：堵转保护（注入前先把 goal 写大或直接 inject stall）
#   arm.sim.inject kind=stall motors=[3] → 500ms 内 state.stalls/event:"stall" 出现，
#      read_register(64,motor=3)==0（torque off）、goal 回退到 present、其他电机正常、无 0x80
# 3) C/E：连接/重连
#   arm.reconnect ×20 + 持续订阅 → 流不断；stats.opens==stats.closes；CPU 不应 100%
# 4) 软限位：写 goal 5000 → clamp 到 4095-margin 且返回 warning；reject 模式 → soft_limit 错误
```

v0.1.0 **无** 注入能力（`SimPort` 永远成功，`src/port.rs:225-269`），要复现 v0.1.0 的 B/C/E，
需要用 **pty 假串口**注入字节：

### 5.2 有硬件层（真机）

> 安全前提：肘部/任何关节堵转不要超过数秒；先卸力/断电再操作；不要用 `sudo` 抢串口。

1. **stall 复现（A/B）**：teleop 跑起来，用手/硬限位挡住从臂肘部（或把从臂某关节 goal 写到行程外），
   观察 `arm.list`：v0.1.0 预期 ~50ms 内 `connected=false`、`read_errors` 增长、CPU 开始 100%；
   v0.2.0 预期 ≤500ms 出现 `event:"stall"`、该电机 torque=0、goal 回退、`connected` 保持 true、无 0x80。
2. **拔插复现（C）**：运行中拔掉 follower USB（或切从臂 12V），`lsof` 观察 fd 仍在、`arm.list` 变 ENOENT；
   插回后 v0.1.0 会 EBUSY/不可恢复；v0.2.0 预期 3 次传输层失败后 `Link::close()`、下一周期重新 open，
   `lsof` 每设备 1 fd、自动恢复。
3. **Reboot 复现（D）**：真机 stall 使舵机 0x80 后，v0.2.0 `arm.reboot motors=[3]` → 重新 ping 成功、
   `motor_errors` 清除；若舵机仍报 0x80 则需按 §7 的断电兜底（记录结果用于验证"Reboot 依赖可通信"假设）。
4. **完整重启对照（现场已验证）**：`launchctl bootout gui/$(id -u)/com.armd` + `bootstrap`，新进程两臂 60Hz、
   每设备 1 fd（参考本报告 23:52:56 实测）。

## 7. 未决问题与限制

### 7.1 EEPROM 限位对连续关节 wrap 的影响（⏳）

- XL 系列 `Present_Position` 是单圈 0..4095；本机两臂的 `shoulder_pan`/`wrist_roll` 属可连续旋转关节
  （遥操作按"取离当前位置最近的等价角"处理，见 zeropose 文档）。**EEPROM `Min/Max Position_Limit` 会把这个
  连续空间截断**：当目标跨 0/4095 边界或需要多圈时，软限位 clamp 会把 goal 夹到错误区间，导致"关节不动/反向"。
- v0.2.0 的软限位配置是 **arm 级**（`soft_limits`/`soft_limit_mode`/`soft_limit_margin`），没有 per-joint 开关；
  profile schema 里有 `spin?` 字段（viking 记录），可作为"排除连续关节"的线索，但设计文档尚未定义联动。
- 建议：v0.2.x 增加 per-joint 软限位策略（连续关节默认 disabled 或改为"±行程"），并在标定流程里验证
  0 点附近的跨圈运动；已知坑 2（EEPROM 限位过期/不含当前姿态）也要在启动自检中处理。
- 另注：`docs/SAFETY-DESIGN.md` §3.4 行为 2 只做"读 limits + 未知则 warning"，**未**实现"当前姿态不在限位内时
  自动修正"（该逻辑目前仍在 teleop 侧）——是否下沉到 armd 未定。

### 7.2 Reboot 依赖舵机仍可通信（⏳ 待真机复现验证）

- 本次 0x80 锁存后，舵机**仍能回状态包**（否则现象会是 Timeout 而非 Device 错误），因此 Reboot(0x08)
  大概率可通过同一总线送达；但这是推断，需真机验证。
- 若总线/电源/舵机固件彻底失联（Timeout/CRC 全失败），Reboot 不可达，"物理断电"仍是唯一手段。
- Reboot 后需等待 ~600ms、重新 ping/torque/limits 初始化；若物理上仍顶死在限位，重启后会立即再次 latch
  （应先解除机械力/降 torque 再 reboot）。

### 7.3 物理断电是否仍需要（✅ 本事故中需要；v0.2.0 后待评估）

- 本事故中：**必须**断电才能清 0x80（v0.1.0 无 Reboot/清错通道）。
- v0.2.0 后分类：
  1. 固件 latched 0x80 且可通信 → `arm.reboot` 可能即可（⏳）；
  2. 电气/电源/机械卡死/固件无响应 → 只能断电；
  3. 需要**立即卸掉力矩**的紧急情况 → 断从臂 12V 是最快、最可靠的硬件手段，建议保留该操作规程
     （zeropose 记录也建议"进保护后先断从臂 12V，再完整重启 armd"）。
- 结论：Reboot 可降低断电频率，但"物理断电"应继续保留为兜底与紧急手段；是否仍作为标准恢复步骤需真机演练确认。

### 7.4 客户端自动重连语义（⏳）

v0.2.0 计划 `ArmdClient(auto_reconnect=True)`，但以下语义未冻结，需明确：

- **订阅重放**：重连后 sub_id 变化、订阅参数需保存重放；丢帧窗口内 `seq` 跳变，上层（teleop 的 1s 陈旧帧保护）
  如何判定"安全暂停"而非继续跟随？
- **请求幂等性**：`arm.reboot`/`arm.sync_write`/`arm.torque` 重试一次可能造成重复动作；建议只对只读请求自动重试，
  写操作返回明确错误由上层决定。
- **重连风暴**：本次现场出现 87 个堆积的 unix socket fd（客户端反复重连）；自动重连必须指数退避 + jitter +
  连接数上限，否则会打爆 armd 的每连接双线程模型。
- **异常语义**：`BrokenPipeError/ConnectionResetError` 是"自动重连成功后重试一次"，还是直接抛给调用方？
  需要一个可观察的 `on_disconnect/on_reconnect` 契约。
- **多客户端竞争**：重连后拿到的状态可能来自另一客户端刚写入的 goal，遥操作首帧应用"锁当前姿态"流程。

### 7.5 单总线 60Hz 的额外 4B/电机轮询开销预期（⏳ 需实测）

- 轮询窗口从 `(132, 4)` 改为 `(128, 8)`：命令包不变（sync_read 广播一次，含 6 个 id）；
  **每电机状态包 data +4B**（Present_Velocity 4B + Present_Position 4B）。
- 字节/带宽：X 系列状态包 = 11B 固定开销 + data；+4B/电机 × 6 电机 = **+24B/帧**。
  1Mbps、8N1 ≈ 10bit/byte → 24B ≈ **240µs/帧**总线占用；60Hz → **14.4ms/s ≈ 1.44%** 总线利用率增加。
- 时延：`read_us` 预期增加 ~0.2–0.5ms（含舵机处理/回包间隔），需在 air.my 实测确认"不显著上升、
  60Hz 两臂不退化"（设计 §1 回归要求）。
- 其他开销：订阅帧新增 velocity/goals/torque/motor_errors/stalls/limits 等字段 → JSON 序列化 + socket 写出变大；
  慢客户端靠有界队列丢帧（不拖累总线），但 CPU/带宽需在双 60Hz 订阅下压测。
- 另：每秒一次的 `monitor`（144/3，3B/电机）不变；若 v0.2.0 再频繁读 48/50/70 需评估对 60Hz 的影响（设计为启动/按需读）。

### 7.6 其他待确认

1. **握手失败 = 整臂不可用**：v0.2.0 改为"≥1 个电机响应即 connected"（设计 §3.4 行为 1），需验证 0 个响应 vs
   单电机 error 的边界，以及恢复后 `no_response` 标记的清除时机。
2. **重连失败事件广播**：本次 `frames_published` 在 `polls=0` 时仍持续增长（每次失败×订阅者数），
   可能掩盖真实故障；建议对"重连失败"事件限流或改用 `stats` 计数。
3. **日志可观测性**：v0.1.0 仅有启动日志，事故中无法从日志定位（只有 `ps` 暴露 100% CPU）；
   建议 v0.2.0 对 connected 变化/重连失败/reboot/stall 增加日志（或结构化事件落盘）。
4. **监控口径**：只看 socket 存活会漏报（事故中 RPC 一直可用）；建议监控 `connected`、`polls/seq` 增量、
   进程 CPU 与每设备 fd 数。
5. **现场时间线待 lead 确认**：viking「事故记录」（~23:10）称已 bootout+bootstrap 恢复，但 23:23 启动的
   PID 77101 在 23:25–23:52 仍故障；恢复点是 23:52:56。中间是否复发、断电重枚举的准确时刻需核对操作记录。
6. **v0.1.0 二进制仍在跑**：恢复后的 PID 84036 仍是 v0.1.0（`ping` 返回 `version=0.1.0`），
   即当前现场仍是"带根因的旧版本"，只是暂时健康；部署 v0.2.0 前不要再用 teleop 顶限位。

### 8.3 宿主机计时异常说明（影响所有进程，不是 armd 回归）

部署验收时发现 air.my 的 OS 定时器严重退化，实测（Rust/C 最小程序，与 armd 无关）：

- `nanosleep(2ms)` 实际 ≈ **11.5–12ms**；`nanosleep(16ms)` 实际 ≈ **120–130ms**；
- 根因方向：内存压力（PhysMem 15G/16G used、compressor ≈5G、swap 1.67G/2G used、swapouts 115k，616 进程）；
- **v0.1.0 与 v0.2.0 在同一环境下 poll 频率同为 ≈59Hz**（A/B），因此不是本次改动引入的退化；
  在无内存压力的 sim/空闲环境下 integration 测试可稳定 60Hz。真机“严格 60.0Hz”需待宿主机内存压力
  恢复后复测（`scripts/fd_reconnect_test.py` / 本报告 §5.3 可复用）。
